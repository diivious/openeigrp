# RFC 7868 and OpenEIGRP

Copyright (C) 2026 Donnie V. Savage

## 1. Scope

This document records the protocol specification used by OpenEIGRP and defines
how RFC 7868 relates to project design documents.

It is a reference/authority document. It does not duplicate the RFC text and it
does not describe portable implementation internals.

## 2. Protocol reference

**RFC:** 7868
**Title:** *Cisco's Enhanced Interior Gateway Routing Protocol (EIGRP)*
**Published:** May 2016
**Category:** Informational
**RFC Editor:** https://www.rfc-editor.org/rfc/rfc7868.html
**Plain text:** https://www.rfc-editor.org/rfc/rfc7868.txt

The published RFC title continues to use **EIGRP**. OpenEIGRP is the project
name, not a replacement name for the protocol standardized by RFC 7868.

## 3. Authority in this project

RFC 7868 is the primary reference for protocol behavior and wire semantics.
OpenEIGRP specifications document implementation choices where the RFC leaves
room for internal design, scheduling, ownership, or presentation decisions.

FRR, Unix, BIRD/BSD, and other routing stacks are integration hosts and do not
override protocol semantics. Existing source behavior that conflicts with RFC
7868 is a defect unless an intentional interoperability choice is explicitly
documented in the owning specification.

## 4. How the repository uses the RFC

The RFC defines protocol behavior and wire semantics. OpenEIGRP specifications
then define how this implementation organizes that behavior.

Use these documents for implementation details:

- `eigrp/specs/dual.md` — DUAL state-machine ownership and invariants;
- `eigrp/specs/route-selection-spec.md` — topology-path ordering and successor
  selection;
- `eigrp/specs/rtp.md` — packetization and Reliable Transport Protocol design;
- `specs/architecture.md` — repository-wide ownership and portability rules;
- `specs/platform-integration.md` — public host-integration contract.

The implementation specs may clarify data ownership, scheduling, APIs, and
internal invariants. They may not silently redefine on-wire EIGRP behavior.

## 5. Behavior not fully specified by RFC 7868

When RFC 7868 does not fully determine an implementation choice, use the
ownership and authority rules in `specs/architecture.md`.

A choice that has no wire-visible effect may be an OpenEIGRP implementation
detail. A choice that affects interoperability must be documented with its
protocol rationale.

Cisco operational behavior may be consulted for compatibility, especially for
CLI presentation, logging, or behavior not normatively described by the RFC,
but it is not a substitute for project design review.

## 6. Scope exclusions

EIGRP Stub runtime behavior is outside OpenEIGRP project scope. Existing
configuration references may remain where required for compatibility or source
history, but new Stub runtime implementation and tests are not part of the
project target.

## 7. No forked RFC text

Do not copy the full RFC into this repository and edit it as an OpenEIGRP
specification. Link to the RFC Editor version and document implementation
choices in the owned OpenEIGRP specification instead.
